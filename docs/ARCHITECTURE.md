# Apps Холодосов — архитектура и модель решений

> Принцип продукта: **пользователь не анализирует данные — система анализирует данные.**
> Пользователь видит только: ЧТО переместить · ОТКУДА · КУДА · СКОЛЬКО · ПОЧЕМУ · НАСКОЛЬКО СРОЧНО.

> **Обновление (production):** состояние хранится в PostgreSQL (`STORE_DRIVER=postgres`, `src/lib/store/pgStore.ts`), файл `.data/` —
> только для разработки. Вход — учётные записи + PIN, роли EMPLOYEE / MANAGER / ADMIN, отзываемые сессии (docs/SECURITY.md).
> Клиенты: desktop web, PWA `/m`, Android (Capacitor, открывает прод-сервер) — docs/ANDROID.md, docs/DEPLOYMENT.md.

## 1. Анализ задачи

| Что есть | Что нужно |
|---|---|
| ~15 холодильников с разным поведением клиентов | Автоматически определить «норму» каждой точки |
| Ручная проверка остатков каждый час | Раз в час — готовый короткий список миссий |
| Внешний KitShop API | Только чтение. Никогда не пишем |
| ≥ 6 месяцев истории продаж | История напрямую влияет на каждый прогноз |

Суть задачи — **перераспределение запасов (lateral transshipment)** между точками одной сети
в течение дня. Две противоположные цели:

1. **Доступность** — холодильник не должен пустеть по востребованной категории.
2. **Списания** — к закрытию не должно оставаться скоропортящейся еды.

Перемещение из A в B одновременно снижает риск списания в A и риск пустой полки в B.
Движку нужно найти пары, где обе стороны выигрывают, и не создать новую проблему у источника.

Ключевые сложности:
- спрос сильно зависит от часа, дня недели, точки и категории;
- продажи — это **урезанный спрос**: пустой холодильник показывает 0 продаж, но спрос был;
- у одной точки разный рабочий график, праздники, «завтра выходной» меняют вечернюю логику;
- много шума: нужен прогноз с интервалом и уверенностью, а не одно число;
- доверие людей: каждая рекомендация должна объясняться простыми числами.

```
│        │  fetch /api/*  (никаких credentials на клиенте)                        │

│  API routes (server only)                                                      │
│        │                                                                       │
│  Runtime ── DataSource (interface) ──┬── MockDataSource (Simulator)   ← PHASE 1│
│        │                             └── KitShopDataSource (read-only)← PHASE 2│
│        │                                    └── services/kitshop/* (GET only)  │
│        ▼                                                                       │
│  Engine (pure functions, без I/O)                                              │
│   history → forecast → risk → profile → recommend → scoring → feedback         │
│        │                                                                       │
│  AppStore (наши данные: миссии, XP, bias, статистика пар)                       │
│   MVP: JSON-файл .data/app-state.json   →   PHASE 2: PostgreSQL + Prisma        │
└────────────────────────────────────────────────────────────────────────────────┘
```

Решения:
- **Engine — чистые функции.** На вход — `NetworkSnapshot` (справочники + куб истории + сегодня + остатки),
  на выход — состояния, прогнозы, миссии. Одинаково работает с симулятором и реальными данными,
  легко тестируется.
- **DataSource — единственная точка входа данных.** Симулятор и KitShop реализуют один интерфейс.
- **KitShop-слой физически не содержит методов записи** (см. §8).
- **MVP без обязательной БД**: состояние хранится в JSON-файле, чтобы симулятор запускался `npm run dev`.
  Схема Prisma для PostgreSQL уже описана (`prisma/schema.prisma`) и подключается в Phase 2 за тем же интерфейсом `AppStore`.

## 5. Алгоритм рекомендаций

Все параметры — в `src/lib/config/engine.ts`.

### 5.1 Базовая линия из истории (baseline)

Для точки *f*, категории *c* и каждого часа *h* сегодняшнего дня:

1. **Выборка аналогичных дней.** Дни, когда точка работала (по графику, не праздник, продажи > 0):
   - уровень A — тот же день недели;
   - уровень B — тот же тип дня (будни/выходные);
   - уровень C — сеть: похожие точки (тот же тип локации), затем вся сеть, нормированные по объёму точки.
2. **Взвешенная давность (weighted history).** Дни бьются на корзины по возрасту:
   `0–7 д: 40%`, `8–30: 30%`, `31–90: 20%`, `91–180: 10%`. Среднее по корзине, затем взвешенное
   среднее корзин (веса пустых корзин перераспределяются). Выбросы обрезаются: значение > медиана × 1.8 → медиана × 1.8
   (одна аномалия не переписывает профиль).
3. **Иерархия со сжатием (shrinkage):**
   `base = wA·A + (1−wA)·(wB·B + (1−wB)·C)`, где `wA = nA/(nA+4)`, `wB = nB/(nB+6)`.
   Мало данных → автоматически больше веса сети (cold start).
4. **Поправки:** тренд (последние 28 дней vs взвешенное среднее, мягко, 0.85…1.2),
   фаза месяца (начало/конец месяца из истории, 0.92…1.08), bias из обратной связи по миссиям (0.6…1.4).

Результат — `normalExpected[h]`: сколько точка *обычно* продаёт в этот час.

### 5.2 Темп дня (pace) — «сегодня vs нормальный вторник»

```
expectedSoFar = Σ normalExpected по прошедшим четвертям часа (без интервалов, где категория была на нуле)
actualSoFar   = Σ продаж за те же интервалы
rawPace       = actualSoFar / expectedSoFar
fridgePace    = 1 + w·(rawPace − 1),  w = expectedSoFar / (expectedSoFar + 8)     // сжатие к 1
catPace       = fridgePace сжатый в сторону сырого темпа категории тем же способом
pace          = clamp(catPace, 0.5, 1.8)
forecast[h]   = normalExpected[h] · (1 + 0.8·(pace − 1))
```
Интервалы, когда категория была пустой, исключаются из обеих сумм: нулевые продажи при пустой полке не означают нулевой спрос.

### 5.3 Прогноз, интервал, уверенность

- `expected_1h`, `expected_2h`, `expected_until_close` = сумма `forecast[h]` по окну (с долями часа).
- Интервал: `sd = √(E + 0.5·(cv·E)²)`, диапазон `[E − sd, E + sd]`, где `cv` — вариативность дневных продаж категории.
- Уверенность: `0.15 + 0.85 · min(1, nA/12)^0.6 · (1 − min(0.6, cv)) · (1 − min(0.4, 0.6·|pace−1|))`, × 0.8 при аномалии,
  затем ограничение 20…97%.
- **Аномалия**: прогноз дня > μ + 2.5σ (или < μ − 2.5σ) по аналогичным дням и темп > 1.35 (< 0.65) → флаг ANOMALY.
  Прогноз на сегодня повышается через pace, долгосрочный профиль не меняется.
- Прогноз по товарам = прогноз категории × доля товара в точке (последние 30 дней, сглажено к сети).

### 5.4 Состояния риска (по точке × категории)

```
projected_2h    = stock − expected_2h
projected_close = stock − expected_until_close
safety          = max(2, 0.5 · expected_1h)

EMPTY_RISK (CRITICAL) : projected_2h ≤ 0            и expected_2h ≥ 1
LOW_STOCK  (WARNING)  : projected_2h < safety
WASTE_RISK            : waste_units ≥ 3
OVERSTOCK             : stock > expected_until_close · 1.8  и  излишек ≥ 4
NORMAL                : иначе
```
`waste_units = max(0, projected_close) × waste_share(срок годности, работает ли точка завтра)`
— например, салат (1 день) → 100%; горячее (2 дня) → 50%, если завтра рабочий, и 100%, если завтра выходной.
Поэтому вечером перед выходными движок сам начинает «спасать» скоропорт.

### 5.5 Источник и получатель

```
Получатель (TARGET):
  cover      = min(3 ч, время до закрытия)
  deficit    = ceil(expected_cover + safety − stock − inbound)      // дефицит
  capacity   = floor(0.8 · expected_until_close − stock − inbound)  // сколько может продать до закрытия
  только открытые точки, открытые ещё ≥ 1 ч

Источник (SOURCE):
  keep         = max(expected_next_check_2h + safety,  expected_until_close_upper)
  transferable = floor(stock − keep − outbound)      // безопасный излишек
  закрытые точки по умолчанию не источник
```
`expected_until_close_upper` берёт верхнюю границу интервала, если уверенность низкая, — поэтому
при слабых данных источник отдаёт меньше и сам не опустеет через 1–2 часа.

### 5.6 Кандидаты, количество, приоритет

Для каждой категории, для каждой пары (s, t):
```
qty = min(transferable_s, max(deficit_t, rescue ? min(capacity_t, waste_s) : 0))
qty = floor(qty · (0.6 + 0.4 · confidence_t))     // осторожность при низкой уверенности
qty ≥ 2, иначе отбрасываем

shortage_risk     = min(1, deficit_t / max(expected_2h_t, 1))  (+0.2, если опустеет в течение 1 ч)
waste_reduction   = min(1, min(qty, waste_s) / 6)
sales_opportunity = min(1, min(qty, capacity_t⁺) · pairSuccess / 8)
urgency           = clamp(1 − hours_to_empty_t / 3, 0, 1)

raw      = 0.35·shortage + 0.25·waste + 0.25·opportunity + 0.15·urgency
priority = 100 · raw · (0.7 + 0.3·confidence) · distanceFactor · pairFactor
```
- `distanceFactor = clamp(1.1 − 0.02 · travel_minutes, 0.5, 1.1)`; маршруты длиннее 45 минут отбрасываются.
  Время в пути — из ручной матрицы или по координатам.
- `pairFactor` — сглаженная историческая успешность маршрута `(продано + 3·0.75)/(перенесено + 3)`, нормированная к 0.75.

### 5.7 Отбор (не перегружать сотрудников)

Жадный отбор: лучший кандидат → вычесть объём из излишка источника и дефицита получателя → пересчитать → повтор.
Ограничения: ≤ 5 маршрутов, ≤ 2 миссии с одного источника, priority ≥ 35.
Линии с одинаковым маршрутом объединяются в одну миссию («одна поездка»).
Принятые и выполняемые миссии резервируют объёмы, поэтому новый анализ их не дублирует.

### 5.8 Обратная связь

Через 2 часа после выполнения:
```
sold_attributed = clamp(sales_target_in_window − stock_target_before, 0, moved)
success         = sold_attributed / moved   → EXCELLENT ≥ 0.8, GOOD ≥ 0.5, WEAK ≥ 0.25, POOR
accuracy        = 1 − |actual − predicted| / max(predicted, 1)
bias(t, c)     ← 0.8·bias + 0.2·(actual / predicted)       (ограничение 0.6…1.4)
pairStats(s→t, c) += moved, sold
```
Перенесли 6, продали 1 → прогнозы этой точки по категории снижаются, маршрут получает штраф.

## 7. Симулятор (MOCK MODE)

- 15 точек с разными архетипами (любители горячего, десертов, утренние/вечерние пики, 5/6/7-дневные графики,

  продажи — пуассоновские случайные величины, генерация детерминирована по seed (одинаковые данные после перезапуска).
- 180 дней истории + праздники (точки закрыты).
- Живой день: шаг 15 минут, продажи ограничены остатком (упущенный спрос считается), утренняя поставка
  планируется по **средней по сети** структуре → у точек с перекосом появляются дефициты и излишки, как в жизни.
- Конец дня: списание по сроку годности; если завтра выходной — списывается больше.
- DEV PANEL: +15 мин / +1 ч / +3 ч, всплеск продаж, дефицит, излишек, аномалия спроса, сброс дня, пересоздание.

## 8. KitShop API: безопасность и требования

См. `docs/KITSHOP_WRITE_API_AUDIT.md` (официальная API v1.3) и `docs/KITSHOP_API_REQUIREMENTS.md`. Кратко:
- транспорт `src/services/kitshop/transport.ts`: POST + `Auth{CompanyId, RequestId, UserLogin, Sign=MD5}`, строго растущий RequestId, запросы по одному;
- read-клиент `kitshopClient.ts` — только `get*` из белого списка (`GetShops`, `GetProducts`, `GetShopStocks`, `GetSales`, `GetFillUps`, `GetFillUpById`);
- запись — `src/lib/kitshop-ops` (журнал операций, статусы DRAFT…WAITING_FOR_CONNECTION, идемпотентность по `operation_uuid`,
  перенос = СНЯТИЕ в источнике + ЗАГРУЗКА в цель) и адаптеры: mock (по умолчанию), dry-run, live (`writer.ts`, только за шлюзом флагов);
- сопоставление товаров: id → штрихкод → артикул; название — только подсказка (`mapping.ts`);
- вызовы выполняются только на сервере, credentials — только из env.

## 9. Риски и edge cases

| Риск | Что делаем |
|---|---|
| Продажи ≠ спрос (пустая полка → 0) | исключаем интервалы с нулевым остатком из pace; в Phase 3 — восстановление спроса по InventorySnapshot |
| Нет метода остатков в API | остатки = поставки − продажи ± наши переносы; нужен метод остатков или поставок |
| Перенос выполнен, KitShop не знает об этом | храним `Transfer`, корректируем видимый остаток до следующего снимка |
| Аномальный день (мероприятие) | флаг ANOMALY, временное повышение через pace, профиль не меняется |
| Новая точка | shrinkage к похожим точкам и сети, низкая уверенность → осторожные объёмы |
| Праздники / изменения графика | календарь исключений; дни с 0 продаж при «рабочем» графике считаются закрытыми |
| Часовые пояса | всё внутри — «настенное» время точки; конвертация на границе адаптера |
| Дубликаты продаж при sync | уникальный `external_sale_id`, upsert |
| Возвраты / отрицательные продажи | учитываются как отрицательное количество в агрегате |
| Пинг-понг перемещений | резерв объёмов принятых миссий; одна точка не может быть и источником, и получателем одной категории |
| Точка скоро закрывается | не получатель, если открыта < 1 ч; вечером приоритет — спасение скоропорта |
| Перегрузка людей | ≤ 5 миссий, объединение маршрутов, порог приоритета |
| Ошибки API / лимиты | повторы с экспоненциальной задержкой, инкрементальный sync, UI показывает «данные устарели» |
| Утечка credentials | только server-side env, `.gitignore`, ни одного `NEXT_PUBLIC_*` для KitShop |

## 10. Модель времени (без «офисных часов»)

Холодильники работают по-разному: вечером, ночью, в выходные, 24/7, по разному графику в разные дни. Поэтому:

- **История — все реальные продажи 00:00–23:59, все 7 дней.** День считается выборкой, если в этот день были продажи
  (`history.ts → sample`). Расписание из Настроек больше не отбрасывает ни одной продажи.
- **Профиль день недели × час** для каждой точки (`engine/activity.ts`): средние продажи и частота продаж по каждому часу каждого дня недели.
  Из него — **observed active hours** (непрерывные окна, в том числе через полночь: «Сб 22:00–02:00»), пиковые часы,
  доля ночных (22:00–06:00) и выходных продаж.
- **График из Настроек — подсказка.** Он используется только для дней недели без истории (cold start) и как слабый prior
  в P(точка продаёт в этот день недели). Если по графику «закрыто», а продажи есть — **SCHEDULE MISMATCH** (страница точки, Analytics → Время).
  Закрытие раньше открытия (18:00–02:00) — работа через полночь.
- **«Сегодня» — календарный день** по местному времени: продажа в 01:15 относится к новому дню.
- **Прогноз** строится на сегодня и на завтра (24 + 24 часа); окна считаются от текущей минуты и могут переходить через полночь
  (`forecast.ts → sumAcross`). Активна ли точка сейчас — по истории этого часа этого дня недели или по продажам за последний час.
- **Горизонты** (`recommend.ts → horizonWindow`): REAL TIME (~90 мин), +1 Ч, +2 Ч, ДО HH:MM (время в Настройках, по умолчанию 20:00;
  после него режим «прошёл» и используется REAL TIME), ДО КОНЦА АКТИВНОСТИ (конец наблюдаемого окна точки, максимум 12 ч).
  Нигде нет системного 18:00 или 09:00.
- **Симулятор** моделирует разные паттерны: ночная точка (16:00–02:00), 24/7, выходные сильнее будней, разный график по дням,
  продажи в субботу у «офисной» точки; формальный график у всех — Пн–Пт 08:00–20:00, чтобы было видно расхождения.
